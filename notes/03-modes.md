
# 工作模式（ECB / CBC / CTR）实现笔记

## 统一原则

三种模式全部复用 `src/sm4.py` 的 `encrypt_block` / `decrypt_block`，
本模块只负责分组切分、异或链接与填充，绝不在各模式内重复实现 SM4。

- **ECB / CBC**：基于 PKCS#7 填充，密文长度必然是 16 的倍数。
- **CTR**：流模式，不填充，密文长度 = 明文长度。

## ECB

每块独立加密，相同明文块 → 相同密文块。实现最简单，但这是它最大的安全缺陷：
图片中平坦色块区域加密后仍是相同色块，**轮廓清晰可见**（见 `demo/ecb_penguin.py`）。
因此现实场景中几乎不使用 ECB。

## CBC

- 加密：`C[i] = E(P[i] ^ C[i-1])`，`C[0] = E(P[0] ^ IV)`，IV 必须 16 字节。
- 解密：`P[i] = D(C[i]) ^ C[i-1]`，每块只依赖前一块**密文**（不依赖前一块明文），
  因此解密天然可并行。
- **踩坑**：IV 只在第一块参与运算，写错 IV 处理逻辑时典型症状是
  "只能加解密第一个块，后面的块全错"。

## CTR

- 加解密**同一个函数**：`out = data ^ E(counter)`，异或可逆所以对称。
- nonce 作为 128 位大端整数计数器初值，每块 `counter += 1`（含进位）。
- **踩坑**：计数器进位。小数据测试没问题、长数据后半段错，一定是把计数器
  当成"仅低 32 位递增"或"每次重算初值"了。本实现用 `int.from_bytes` 转大整数
  整体递增，天然正确处理进位。

### 踩坑：nonce 重用会毁掉全部安全性（这是 CTR 最该讲清的一点）

这是本项目最容易被追问的地方，单独写清楚。

**推导**：设同一对 `(key, nonce)` 加密了两条消息，密钥流完全相同（记为 KS，因为
KS 只由 key 和 counter 决定，与明文无关）：

```
C1 = P1 ^ KS
C2 = P2 ^ KS
C1 ^ C2 = (P1 ^ KS) ^ (P2 ^ KS) = P1 ^ P2        # KS 被消掉
```

攻击者不需要密钥，只要拿到两条密文相异或，就得到**两条明文的异或值**。
这叫「两条密文流异或攻击」。历史上 Venona 项目正是靠这种重合（one-time pad 被
重复使用）破译了大量电报。

进一步：如果其中一条明文已知或可猜（文件头固定、HTTP 请求格式固定、纯文本），
另一条就被逐字节还原。

**结论**：CTR 的安全性完全建立在「同一 key 下 nonce 绝不重复」上，这是它和
一次性密码本共享的软肋。工程上有三种处理方式：

1. 每次加密随机生成 nonce（本项目的 CLI 就是 `os.urandom(16)`），代价是随机数
   要够好、且同 key 下碰撞概率可忽略（128 位随机数足够）；
2. 用「静态前缀 + 单调计数器」结构，保证跨进程不重用；
3. 干脆换 GCM/CCM，让 nonce 重用能被认证标签检出（虽然 GCM 的 nonce 重用同样
   会泄露认证密钥，只是失败的更早更明显）。

**本库的边界**：`ctr_crypt` 只校验 nonce 长度是 16 字节，**不检测重用**——
库没法知道你是不是又用了一次同一个 nonce。这一点在 README「已知限制」里写明了。

### CTR 的一个容易忽视的性质

CBC 里改一个密文字节，会影响该块和下一块；ECB 里改一个字节只影响那一块。
**CTR 里改密文第 i 个字节，只影响明文第 i 个字节**——因为 `P[i] = C[i] ^ KS[i]`，
逐字节独立。好处是可随机访问（seek 到任意偏移直接算），坏处是攻击者能精准
翻转明文的任意比特，而且没有任何检错。这又是「需要 AEAD」的理由。

## PKCS#7 填充

- `pad`：补 `n = 16 - len%16` 个值为 `n` 的字节；长度正好是 16 的倍数时
  `n = 16`，必须额外补一整块——否则 `unpad` 无法区分"恰好对齐"与"缺一块"。
- `unpad`：取末字节 `p`，校验 `0 < p <= 16` 且末尾 `p` 字节全部等于 `p`，
  否则抛 `ValueError`，并区分「长度非法」（空数据/非块长倍数/填充值越界）
  与「填充字节非法」（末尾字节与填充值不一致）。

## 三种模式共同缺失的能力：完整性

ECB / CBC / CTR 都只提供**机密性**，不提供**完整性/认证**。

- 密文被篡改，解密仍然成功返回结果（ECB 只坏一块、CBC 坏两块、CTR 只坏对应字节），
  但库无法告诉你"被改过"。
- CBC / CTR 都没有身份绑定，攻击者可以拼接、翻转比特做定向篡改（CTR 尤其精准）。
- `unpad` 会报错，但"报错 / 不报错"的差异本身就是信息泄露——这就是
  **padding oracle 攻击**的入口。真实系统要么用 AEAD，要么把失败统一成同一种。

**下一步的自然延伸**：加 GCM/CCM 一类 AEAD 模式，用认证标签把完整性和机密性一起解决。

## 参数校验

- CBC IV、CTR nonce 都强制 16 字节，不对直接抛 `ValueError` 给提示。
- 密文长度非 16 倍数（ECB/CBC 解密）同样报错。

## 验收结果

- 三模式往返测试覆盖 0 ~ 1000 字节多种长度，全部通过。
- ECB 相同块 → 相同密文块 ✓；CBC 换 IV 结果不同 ✓；CTR 同一函数对称 ✓。
- 参数错误全部给出人话提示 ✓。
